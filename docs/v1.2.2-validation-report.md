## 实现

- Issue 增加status、blocking、activity_id、target、source、evidence，severity限定info/warning/error。schema拒绝unverified/informational的blocking组合。
- 已知开放时间外安排为OPENING_HOURS_CONFLICT；开放时间缺失为OPENING_HOURS_UNVERIFIED。
- 天气只使用现有tool记录和有效日期证据；缺失/过期为WEATHER_UNAVAILABLE；严重天气+明确户外为WEATHER_CONFLICT；严重天气但景点环境不明为WEATHER_EXPOSURE_UNVERIFIED。
- 交通候选按起点、终点和日期映射。模型遗漏ID时从现有匹配候选补齐；不生成车次。真实缺失是TRANSPORT_UNVERIFIED。已知进站缓冲或换乘下限不满足是TRANSPORT_CONFLICT，即使跨站路线未知也不能抹去已知无法赶上的事实。
- 费用单位为分：known_cost排除估算项目，estimated_cost包含估算，unknown_cost_items保留缺价项目，budget_limit保留上限。已知下限超预算才阻断；估算超限为BUDGET_RISK；缺价为BUDGET_PARTIAL。
- 酒店未知路线为HOTEL_ROUTE_UNVERIFIED，不重选。已知15km以上地理距离、60分钟以上POI通勤、75分钟以上车站接驳分别保留证据并可阻断；仍只有原有最多一次酒店重选。
- 以(day,type,activity_id或target)去重。同日不同POI保留各自证据，天气按城市/日期合并，酒店各路线目标保留。旅行模式进一步按类别聚合，演示模式保留全部详情。
- Critic仅依据blocking问题请求重规划；原有最多2次、重复问题停止机制保留。validation_history只含应用生成的校验记录，不暴露模型隐藏推理。
- completed为事实充分且无阻断；partial为无阻断但外部信息待验证（运行受限也继续保留原有受控partial语义）；conflict为存在确认阻断。失败/取消/澄清状态保持原路径。

## Baseline 检索失败的隔离诊断

正式Baseline前几题反复搜索POI、缺少目的地活动并达到MAX_STEPS。额外一次隔离诊断仅用了2次Qwen调用（5,186 tokens），不计入或替换任何正式case结果：模型将POI关键词改成组合字符串“历史 夜景”，三个城市的固定fixture均返回empty。现有fixture只按完整字符串匹配名称或单个tag，并不支持组合关键词检索；后续正式Trace可见重复POI查询与重复调用拦截。诊断不能证明每一道失败都由同一参数造成。

对照使用确定性模型+真实本地MCP，两系统A01都成功取得相同景点、天气与路线，未发现协议丢数据。原Baseline、MockAmapProvider的该关键词匹配规则和Dataset均未为此次评测改变。此次没有为抬高或压低成绩改动Provider或标签；后续若扩展fixture搜索语义，应两组统一并全量重新评测。

这暴露了合成工具环境与模型工具参数选择的敏感性；Baseline下降不能直接解读为Critic修复带来的架构收益。证据：[隔离诊断](v122-baseline-diagnostic.json)、[协议对照](v122-protocol-preflight.json)。

历史V1.2 Baseline在A类也仅2/10，本轮A类0/10；因此不能将这类检索失败描述为本轮新引入的协议故障。它是既有严格fixture关键词环境下，模型工具选择的一项已复现局限。

# TripPilot V1.2.1 产品化验收

本轮只修改澄清契约、日程规则及展示层。没有新增 Agent，没有重构 LangGraph、MCP、A2A、Harness、Memory、Provider 架构或 Benchmark。Amap Provider 只有兼容天气字段映射的 9 行新增/1 行替换。

## 1–2. Clarification 定位与修复

沿 RequestPanel payload → PlanRequest → RunService → Supervisor structured output → GraphState → PlanResponse → Clarification UI 完成核查。

- **未复现历史描述中“已经传 start_date 仍阻塞”的同一故障**，没有历史失败请求/模型输出，不能编造根因。修改前的真实 Qwen 最小验证已得到 origin=上海、destinations=杭州/南京/苏州、days=5、start_date=2026-10-10，并继续路由。
- 已复现的实际阻塞字段是 **start_date**：初始表单日期为空时，前端不发送 constraints.start_date；最终真实浏览器清空日期后返回 `missing_fields=["start_date"]`、`questions=["你计划哪天出发？"]`。
- 已确认的契约缺陷：旧响应只有 status 与中文标签 questions，没有标准 missing_fields/needs_clarification；UI 依赖固定标签判断补充输入。
- 现在返回明确布尔值、字段名和自然语言问题，UI 显示“还差一点信息”并按字段名提供输入；已有日期直接传递，Demo 按钮显式传日期。模型提示仅包含显式 session 字段，避免完整默认 null 对象干扰；遗漏的明确出发城市/天数可从用户原话补齐。
- 真正阻塞项只含出发地、目的地、出发日期、天数（或结束日期）；5 天 + 开始日派生结束日 +4。酒店星级、房型、人数等可选细节不阻塞。

## 3–4. 一天一景点的真实根因

DayPlan.activities 原本就是列表，React 原本也用 map 全量渲染，**不是 schema 单项限制，也不是前端 activities[0]**。

根因是三处规划策略共同作用：真实 POI 时 default_selections 强制截为一项；Planner 提示要求转场日只安排一个活动；Local Travel 真实地标候选仅两处。已去掉截断与提示限制，扩大同区域候选并保留原有查询工具与预算。联调另外发现首个城市在 Provider 尚为 PENDING 时会误走泛搜索，已按配置实例选择真实查询策略。

## 5. 向后兼容的 Day schema

保留原有 day/date/city/origin_city、rail/flight、activities、local_legs、costs。新增：

- `activities[]`: 保留 `poi`（name/category/environment/city/coordinates/evidence_id）与 start/end；补充 time_period、estimated_duration（分钟）、route_from_previous、travel_minutes、source、optional、notes。
- `breaks[]`: 用餐/休息的 label/start/end，按实际交通顺延并保留完整一小时。
- `notes[]`: 时长估算、活动因时间窗/交通预算未排入的具体原因。
- `weather`: city、forecast_date、weather_condition、min_temperature、max_temperature、precipitation、precipitation_probability、source、status、evidence_id。

## 6–8. 密度、转场、聚类与时间预算

慢节奏完整日通常 **2 项主要活动**；紧凑模式在证据和时间允许时通常 3–4 项，始终受 max_attractions 上限约束。转场日允许 1–3 项；晚到、暴雨、长时间景点或明确休息可减少数量。

轻量聚类在现有候选中先用地理邻近筛选，再比较完整的高德路线证据进行排序。直线距离只决定候选/选择请求步行或公交，不冒充实际通行时间；最终 travel_minutes 来自已有 Amap Route。短距离优先查步行路线，远距离查公交。每个活动用 visit_minutes 估算、叠加前段交通与餐食缓冲；超过开放/活动时间窗会移除，不能把已经关闭的景点强行放为首项。明显交通超限保留 Critic 冲突，不隐藏。夜景候选可选、按合适时段安排，不每天机械添加。

## 9. Critic Day Quality

新增 DAY_TOO_EMPTY、DAY_TOO_DENSE、EXCESSIVE_TRANSIT、POI_CLUSTER_INEFFICIENT、NO_PREFERENCE_ALIGNMENT。空日检查豁免转场、恶劣天气、明确休息、长游览及短时间窗。绕行判断需要实际路线证据，不能只凭直线距离判冲突。仍复用原有最多 2 次 replanning 与相同 Harness 预算，没有新判断引擎。

## 11–19. 界面与信息层级

| 项目 | 最终行为 |
|---|---|
| 字体 | 主标题32–34px；Section20–24px；Day20–21px；活动18px；正文15–16px；输入16px；元数据13–14px，提高正文对比度 |
| Preferences | 紧凑 chips；无数据为“尚未保存旅行偏好”；展开设置沿用原本本地记忆 |
| Trip Summary | 出发地→目的地、天数、预算、城市数、实际主要交通、节奏，下面为一行天气概览 |
| Day Card | 全量上午/下午/晚上活动、预计时长、交通、用餐休息与当日费用；来源/坐标/路线与费用详情默认折叠 |
| Hotel | 当前城市住宿区域及理由，默认最多3家名称，单家地址/来源/路线折叠；额外候选才显示查看更多 |
| Rail/Flight | 每种方式默认一个代表方案、门到门估计与建议；完整候选和接驳明细展开；DATASET标签保留 |
| Map | 默认当前Day，真实SDK Marker按活动顺序编号，切换fitView；增加顶部留白避免名称裁切，立即调整视野避免动画截图空白 |
| 旅行模式 | 默认模式，隐藏顶层协议和Provider技术状态；进度为中文旅行动作，技术Trace折叠 |
| 演示模式 | 显示真实 Provider、MCP、A2A、Harness、Memory状态与工作流；仅影响UI，切换不会发起规划 |

集中“出行前确认”展示缺失预报、开放时间、交通数据来源和酒店价格/房态说明；完成状态不再悬浮遮挡活动。真实浏览器核对初始页、loading、摘要、Day1–5、详情、酒店、交通、地图、两种模式、Clarification 与偏好控件；390px窄屏无横向溢出。

## Weather UI 补充验收

**之前看不到的原因**：后端 weather_data 原本已在 GraphState、A2A artifact 和 Critic 中使用，但没有投影进 DayPlan/API，React 也没有天气组件；高德适配器还丢弃了 nighttemp。

现在只从既有 `MCP get_weather` 的 WeatherRecord 与 Evidence 投影：城市/日期匹配、非 stale、source=amap_live 且 source_kind=live 才标为 LIVE。高德 daytemp/nighttemp 做兼容字段映射；不向 LLM 请求天气。接口未提供降雨概率时不显示，绝不从天气文字估出百分比。模拟数据另标注且不当真实温度显示。

Day Card 顶部为天气图标/短描述/实际温度，概率或降水量有数据才显示。旅行模式隐藏协议来源；演示模式的真实预报可显示 `Amap Weather · LIVE · MCP get_weather`。Trip Summary 仅显示有可靠forecast的城市/日期，否则“待确认”。“天气可能影响该活动”仅使用既有 Critic WEATHER_RISK，室内不重复警告。

| 南京 | 2026-09-22 | 多云 | 21–27°C | amap_live |
